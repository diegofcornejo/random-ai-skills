# Plan Format — `SECURITY-REMEDIATION.md`

The repo plan is written at the repo root, **in the user's language**. Translate every heading and sentence of the template below; keep package names, versions, GHSA/CVE ids, rule ids, paths, commands and numbers as they are. Before writing it the first time, run the report-file decision (SKILL.md section 7).

Build it only from the spot-checked Analysis Report ([repo-analysis.md](repo-analysis.md)). Numbers (totals, priority, band) are copied from the CLI output, never estimated.

## Alert links

Link every alert to its GitHub page: `https://<host>/<owner>/<repo>/security/<dependabot|code-scanning|secret-scanning>/<number>` (the `html_url` from the CLI output). Write the label as `<source>#<number>`, e.g. `[dependabot#2](https://github.com/acme-telco/portal-web/security/dependabot/2)`. Never write a bare `#2`: GitHub renders it as an issue/PR link.

## Block ordering rule

This is the only place the ordering rule is defined. Other files link here.

1. **Secrets first**: the block for open secret-scanning alerts is always block 1, whatever its band or fix-risk.
2. **Dismissal candidates last**: they close alerts without changing code, so they never delay a real fix.
3. Every other block is ordered by these keys, in this order:
   1. **priority band**: the block's highest alert band, P1 → P2 → P3;
   2. **fix-risk within the band**: `low` → `medium` → `high`;
   3. **tiebreak**: the block's highest priority score, descending;
   4. last resort: the typical order below.
4. **Dependencies win**: if block B can only work after block A (e.g. a library bump that needs Angular 12), A goes before B, and B says "after block A".

Typical blocks (only the ones that apply, numbered in the final order):

1. Secrets: rotate first.
2. Bring in healthy existing Dependabot PRs.
3. Direct dependency patch/minor bumps.
4. Transitive fixes via `overrides` / `resolutions` / `pnpm.overrides` / `composer update <pkg> --with-dependencies`.
5. Angular major upgrade: **one block per major hop** (11→12, 12→13, …), each its own block. Other major upgrades: one block per package.
6. Code-scanning code fixes (one block per rule, or per closely related file group).
7. Dismissal candidates with justification.

Mechanical blocks never mix with application-code blocks: a bump that needs code changes is a major-upgrade or code-change block, not a "direct bump".

## Field rules

- **Who acts** is one or more of: `agent` (mechanical work the agent does once the block is approved), `developer` (approves each code change; may need to decide), `human outside the repo` (provider consoles, vaults, CI/CD secrets, other teams, licensing).
- **Effort** is developer time, including review and verification, not wall-clock CI time.
- **Fix-risk** always lists the factors from [risk-model.md](risk-model.md). A level without factors is not allowed, and a block is never "unrated". Code that can't be inspected is rated `high` ([risk-model.md](risk-model.md#code-that-cant-be-inspected)).
- **Coverage line**: the header always has it, one status per source (`ok`, `not enabled`, `not licensed`, `no permission`, `unavailable`). When every source is `ok`, say so explicitly (`Coverage: Dependabot ok · code scanning ok · secret scanning ok`); silence is ambiguous. Add `CodeQL does not analyze PHP` when the repo has .php files.
- A secret block never puts the secret value, or any part of it, in the plan. Use the type, the alert link, and `path:line`; when the value must be referred to, write `[redacted]` (a type's public prefix such as `AKIA…[redacted]` is allowed).
- Dismissal-candidate blocks list, per alert, the proposed reason (API enum, untranslated) and the draft comment (≤280 characters, in the user's language). Each one is still confirmed individually during execution ([dismissals.md](dismissals.md)).
- If an alert source has no coverage, the summary row says "no coverage" instead of a number.
